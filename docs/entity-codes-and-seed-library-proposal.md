# MICharisma Inc entity codes and replayable seed libraries

Proposal v0.5 · October 5, 2026

This remains the broader design proposal. A first implementation now exists for scoped YAML/JSON, sequence selection, entity codes/aliases, annual team snapshots, and contract-free whole-season rosters. See [the implemented pilot and its limits](yaml-seed-library.md) for the current contract and commands. The other examples, cross-app adapters, public URLs, amendment system, and fan interface below remain proposals. Earlier illustrative sequence allocations are not the installed registry.

## 1. What we want to make possible

The primary goal is a library of hundreds or thousands of seed files that can grow, overlap, and run repeatedly. Files identify entities and relationships without carrying database primary keys. Replaying the library adds missing knowledge, preserves existing data, and can reconstruct deleted catalog records even when their new numeric IDs differ.

The secondary goal is a code a fan can construct from memory. A fan should be able to enter a team, player, pitch, jersey component, race lap, or other subject and see what we know about it. Short or conversational forms can be supported alongside precise import references.

The starting example supplied by Mike is:

```text
MIC-ALA-BKT-NBA-NYK-1985-EWING
```

It identifies Patrick Ewing through the MICharisma namespace, AthleteAce catalog, basketball, NBA, debut team, debut year, and surname.

The system should support these three activities:

1. **Construct:** generate a candidate code from defined identity facts.
2. **Resolve:** recognize different codes and contexts as references to the same thing.
3. **Replay:** use those references to apply durable catalog knowledge without relying on local IDs.

A meaningful code reduces the need to look up an identifier. A registry still establishes which entity an issued code identifies, resolves aliases, and handles genuine collisions. Constructibility and uniqueness are complementary requirements.

## 2. Requirements and proposed defaults

| Requirement from this discussion | Proposed default |
| --- | --- |
| Dash-separated, expandable codes | Dashes separate components; underscores join the words or values within a component. Widths remain variable. |
| Letters, numbers, or combinations | Accept `NBA`, `NWSL`, `F1`, years, natural sequence numbers, and full names. |
| Many codes can point to one thing | One preferred full code plus registered aliases and context-dependent fan queries. |
| Context can use a later team or season | Distinguish the person from an appearance or participation record; a contextual person alias can resolve back to the same person. |
| Repeated seeds preserve existing data | Default to create missing records and preserve existing values and links; report differences. |
| Numeric IDs can change | Resolve every catalog reference through codes; local foreign keys are generated by the importer. |
| Avoid repeated manual entry or ingest | Generate manifests from reproducible source captures; automate clear matches and validations; surface only unresolved identity or factual conflicts. |
| Fans can concoct codes | Allow abbreviations, full names, omitted prefixes, and descriptive input in a separate resolver. |
| Reuse across MICharisma Inc apps | Supply namespace/catalog once for local seeds and records; qualify foreign references and self-contained exports. |
| Optional numeric sequence selection | Configure an exact parsing recipe with `select_entity_sequence` or the seed helper `sequence_is`; the entity code remains unchanged. |

`MIC` is the proposed shared MICharisma Inc namespace. `ALA` and `BKT` retain Mike's supplied wording. `ASC`, `SPD`, and `STC` below are tentative catalog tokens for Ascent, Spindrift, and Stickers Club.

App prefixes prevent cross-catalog string collisions only when their allocation is coordinated. They do not prevent collisions within a catalog, establish public ownership of a namespace, or prove that two differently coded records represent different real-world people.

### Local codes and qualified codes

An AthleteAce-only seed bundle or database need not repeat `MIC-ALA` on every row. The same identity can be represented as:

| Context | Reference |
| --- | --- |
| AthleteAce seed or local record | `BKT-NBA-NYK-1985-EWING` |
| Namespace/catalog supplied separately | `namespace: MIC`, `catalog: ALA`, `code: BKT-NBA-NYK-1985-EWING` |
| Cross-app reference or self-contained export | `MIC-ALA-BKT-NBA-NYK-1985-EWING` |

Put the default namespace and catalog in file metadata or app configuration. Keep the local code in the entity row. If a registry stores records from several catalogs, uniqueness is on namespace + catalog + local code; a single-catalog registry can make the local code unique. Type-specific table indexes alone do not enforce uniqueness across all entity types in one catalog.

Keep qualification available for cross-app relationships, shared registries, external sources, copied references, and exports that travel without their original file header. A foreign reference may use a full code or explicit `namespace`, `catalog`, and `code` fields. The importer validates the scope before interpreting a relative code.

The tables below generally show qualified codes so examples remain self-contained. Their local forms are obtained by removing the known `MIC-{catalog}` prefix; these are two renderings of one identity, not separate aliases that must be stored twice.

### Current scope

Statistics are outside the current implementation scope. Games played and individual appearances may come sooner. Pitch, inning, lap, timing, and score examples here reserve room in the code design; they are not requests to build statistical models now.

Mike has confirmed that the current database is disposable and can be rebuilt completely. The first pilot can start from an empty database and a compatible schema; it does not need to migrate existing identity bindings, preserve current user records, or reconcile legacy rows. This removes transition work from the pilot. The earlier preservation rule still describes ordinary replay after the new catalog is established; no existing database content is a prerequisite for the initial build.

## 3. Identity, aliases, and context

### 3.1 Preferred code

The preferred code is the issued identity reference. Local manifests normally carry its catalog-relative form; cross-app links qualify it or supply equivalent scope metadata. It is generated from a documented identity recipe, checked for collisions, and committed to the library. It does not depend on a database row number or a seed file's position.

For Ewing, the debut context is a stable identity anchor. It is not an instruction to make the Knicks his current team whenever the file runs.

Once issued, a code remains bound to its original identity. Correcting a title, name spelling, date, or debut attribution can add a better preferred alias while keeping old references valid. Changing the preferred spelling is different from silently assigning its previous code to another entity.

### 3.2 Registered alias

A registered alias explicitly points to a preferred identity. For example:

```text
MIC-ALA-BKT-NBA-NYK-1985-EWING
MIC-ALA-BKT-NBA-ATHLETE-NYK-DEBUT_1985-EWING_PATRICK
```

These can identify the same athlete. The second form illustrates an expanded, tagged grammar; it is not a different Patrick Ewing.

An appearance import may carry a season-context person reference such as:

```text
MIC-ALA-BKT-NBA-NYK-SEASON_1994-EWING_PATRICK
```

The alias is admitted only after evidence resolves it to the athlete. The year is explicitly labeled `SEASON`, so it cannot accidentally be read as a debut year. This illustrates the reference format, not an installed historical appearance record.

Registered full aliases have one target in their defined scope. They must be included in the seed library so that rebuilding a database also rebuilds the aliases. Several aliases can target one identity; aliases cannot form cycles or silently switch targets.

### 3.3 Fan query

`NYK-EWING` is useful fan input. It can identify a unique candidate in the selected catalog, or return choices if more than one candidate matches. A common shorthand should not automatically become a permanently exclusive global alias.

The same input can become ambiguous as the library grows. Therefore a fan query is resolved to an issued reference with explicit catalog scope before it is saved in a seed file. Production seed replay never chooses the first matching surname or asks a language model to guess a target.

### 3.4 A related thing gets its own identity

An athlete and a game appearance have separate references:

```text
MIC-ALA-BKT-NBA-NYK-1985-EWING
MIC-ALA-BKT-NBA-NYK-9394-G1-APPEARANCE-EWING_PATRICK
```

The athlete and that athlete's appearance are distinct. A code extending another code does not automatically imply an alias. The entity type and explicit relationships settle that question.

## 4. Components, underscores, and variable widths

A dash separates components. An underscore joins words or subparts that belong to one component. This lets both people and a simple parser recognize boundaries before we add more flexible interpretation.

```text
MIC-ALA-BKT-NBA-ATHLETE-NYK-DEBUT_1985-EWING_PATRICK
MIC-ALA-BKT-NATIONAL_BASKETBALL_ASSOCIATION-NYK-1985-EWING
```

In the first example, `DEBUT_1985` is one component and `EWING_PATRICK` is another. In the second, `NATIONAL_BASKETBALL_ASSOCIATION` is one league component. Three letters, four letters, full words, and mixed numeric forms are all valid.

Each catalog publishes grammar profiles. A seed can optionally select a profile through its parser configuration or helper. Without that selection, exact registered bindings or an unambiguous profile within the declared catalog/type provide deterministic resolution. Code construction does not depend on character widths or a universal number of components.

| Profile | Illustrative local recipe |
| --- | --- |
| Athlete debut, concise | `{sport}-{league}-{debut_team}-{debut_year}-{surname}` |
| Athlete debut, expanded | `{sport}-{league}-ATHLETE-{debut_team}-DEBUT_{year}-{surname}_{given_name}` |
| Team | `{sport}-{league}-TEAM-{team}` |
| Season | `{sport}-{league}-SEASON_{season_label}` |
| Team's numbered game | `{sport}-{league}-{team}-{season}-G{game_number}` |
| Pitch in that game | `{game}-P{pitch_number}` |
| Pitch in an inning half | `{game}-IT{inning_number}-P{pitch_number}` or `{game}-IB{inning_number}-P{pitch_number}` |
| Pitch in an at-bat | `{game}-AB{at_bat_number}-P{pitch_number}` |
| Uniform component | `{uniform_design}-PART_{component}` |
| Driver lap | `{race}-{driver}-L{lap_number}` |
| Goal | `GOAL-{content_key}-{form_key}` |

These are extensible recipes rather than one universal tree. A stadium can serve several sports; a person can compete in several leagues; a practice can be shared by many athletes.

Proposed normalization and interpretation rules:

- Preferred local codes use uppercase ASCII letters, digits, dashes, and underscores. Human spellings remain intact in display and source metadata.
- Dash is the preferred component boundary. Underscore combines names, phrases, dates, tagged values, or other grouped subparts: `JAYDA_G`, `BOTH_OF_US`, `DEBUT_1985`, `2024_2025`.
- The initial parser can split on dashes and interpret each component using its profile. A later parser can also recognize a full name typed with spaces or dashes, but canonical rendering groups it with underscores.
- Case, accents, apostrophes, and punctuation variants can resolve through declared aliases. Normalization must not silently merge distinct people or entities.
- Short labels such as `G20`, `IT4`, `IB4`, `AB3`, `P8`, and `L20` are valid components; expanded labels can be aliases.
- Numeric and fully numeric profiles are also acceptable. Any dictionary mapping a number to a sport, league, team, or person is a published stable vocabulary, independent of database primary keys.
- A date can be one component, `2026_07_04`. An inclusive year interval can use `FROM_1990-THRU_1999`. Season labels retain the league's meaning; their compact expansion is declared by the profile.
- Optional sequence IDs select immutable grammar profiles. Manifest metadata versions the file format and records the registry revision; it never changes an issued code's meaning.
- An appended component can disambiguate a reference, identify a child entity, or select a collection. The profile declares which meaning applies.

Full league names resolve through registered vocabulary: `NATIONAL_BASKETBALL_ASSOCIATION` and `NBA` can identify the same league component.

An interpretation tool, including the user-mentioned Jev if appropriate, can propose a meaning for flexible fan input. The exact Jev component remains to be confirmed. References are validated and rendered deterministically before they enter the library; replay does not depend on an online interpretation service.

### 4.1 Optional numeric entity-sequence selection

A numeric sequence identifies the order and meaning of components and the kind of entity being requested. It is optional parser configuration, separate from the entity's code and from any numeric vocabulary used for teams or leagues. Many thousands of athletes can share one sequence configuration. Selection is an interpretation instruction; it does not change the entity's identity.

Start with four digits, grouped as `05_22`: the first pair allocates a family and the second an exact recipe within that family. Four digits provide 10,000 combinations; reserving `00_00` leaves 9,999 issuable numbers. Group allocation can leave unused space, so this is an initial capacity rather than a permanent maximum. Keep later length extension possible.

These numbers are assigned in a committed MICharisma sequence registry, independent of database auto-increment IDs. They are unique within the MIC namespace across catalogs. Store and exchange their zero-padded string rendering so leading zeroes and grouping survive Ruby, JSON, spreadsheets, and exports. Write `"05_22"` in Ruby: bare `05_22` is an octal numeric literal with value 338, so it cannot preserve the intended sequence identifier.

Proposed initial allocations, not yet installed:

| Sequence | Recipe or component sequence | Result / scope |
| --- | --- | --- |
| `00_01` | `SPORT-{sport}` | Sport identity. |
| `00_02` | `{sport}-LEAGUE-{league}` | League identity. |
| `00_03` | `{sport}-{league}-TEAM-{team}` | Team identity. |
| `00_04` | `{sport}-{league}-SEASON_{season}` | League season. |
| `00_05` | `{sport}-{league}-SEASON_{season}-TEAM-{team}` | Team campaign. |
| `05_22` | `{sport}-{league}-{debut_team}-{debut_year}-{name_key}` | Athlete identity; surname or an underscore-grouped full name. Illustrative allocation for Mike's helper example. |
| `05_23` | `{sport}-{league}-ATHLETE-{debut_team}-DEBUT_{year}-{surname}_{given_name}` | Expanded reference to an athlete identity. |
| `05_24` | `{sport}-{league}-{team}-SEASON_{season}-{surname}_{given_name}` | Contextual reference to a person; membership evidence required. |
| `02_01` | `{sport}-{league}-{team}-{season}-G{game}` | Team-numbered game reference. |
| `02_02` | `{sport}-{league}-{team}-{season}-G{game}-APPEARANCE-{surname}_{given_name}` | Athlete appearance in that game. |
| `02_03` | `{sport}-{league}-{team}-{season}-G{game}-P{pitch}` | Pitch ordinal within the game. |
| `02_04` | `{sport}-{league}-{team}-{season}-G{game}-IT{inning}-P{pitch}` | Pitch ordinal within an inning's top half. |
| `02_05` | `{sport}-{league}-{team}-{season}-G{game}-IB{inning}-P{pitch}` | Pitch ordinal within an inning's bottom half. |
| `02_06` | `{sport}-{league}-{team}-{season}-G{game}-AB{at_bat}-P{pitch}` | Pitch ordinal within an at-bat. |
| `03_01` | `{sport}-{league}-{team}-UNIFORM-{season}-{edition}` | Uniform design. |
| `03_02` | `{sport}-{league}-{team}-UNIFORM-{season}-{edition}-PART_{part}` | Uniform component. |
| `04_01` | `{sport}-{league}-RACE-{year}-{race}-L{lap}` | Race-wide lap. |
| `04_02` | `{sport}-{league}-RACE-{year}-{race}-{surname}_{given_name}-L{lap}` | Driver lap. |
| `10_01` | `PERSON-{surname}_{given_name}` | Ascent person reference. |
| `10_02` | `OFFICE-{country}-{region}-{chamber}-AD_{district}` | New York-style Assembly office recipe, not every office type. |
| `20_01` | `PRINCIPAL-{surname}_{given_name}` | Spindrift human Principal. |
| `20_02` | `WORK-{artist}-{title}` | Musical Work with resolved credits. |
| `30_01` | `CONTENT-{content_key}` | Stickers Club Content. |
| `30_02` | `GOAL-{content_key}-{form_key}` | Stickers Club Goal. |

Each entry declares allowed catalogs, domain/result type, exact component order, vocabulary and normalization, scope of years and ordinals, allowed aliases, and required identity evidence. The table names candidate recipes; it does not settle unresolved league-specific counting rules. Future recipes remain design-only until supported and fully specified.

Proposed parser API:

```ruby
parser = MICharismaEntityParser.select_entity_sequence("05_22")
parser.resolve("BKT-NBA-NYK-1985-EWING")
```

The class method returns a configured parser instance. Namespace and catalog can come from the AthleteAce seed runner. It does not change process-wide parser state.

Proposed seed-library helper:

```ruby
sequence_is "05_22"

entity "BKT-NBA-NYK-1985-EWING",
  first_name: "Patrick", last_name: "Ewing"
entity "BKT-NBA-CHI-1985-OAKLEY_CHARLES",
  first_name: "Charles", last_name: "Oakley"
```

The `entity` calls illustrate a proposed definition DSL, not a complete runnable seed: required parents and model associations still come from the full bundle. Here `05_22` selects the debut-context athlete recipe for subsequent calls in this file. The number does not appear in either entity code, alias, public URL, or required database field.

For a mixed seed file, a block can limit the selection:

```ruby
sequence_is "05_22" do
  entity "BKT-NBA-CHI-1985-OAKLEY_CHARLES",
    first_name: "Charles", last_name: "Oakley"
end
```

Each file gets a fresh context. A block restores its previous context even after an error; concurrent imports use independent contexts. The no-block form lasts until another selection or the end of that file. Neither form can leak a selection into the next file. A selected sequence applies strictly; an incompatible code produces an error rather than silently trying another recipe.

With no selection, resolve an exact registered code or an unambiguous construction using declared catalog/type context. If several recipes could interpret it differently, report ambiguity and request an explicit sequence or a more explicit code. Ordinary seed replay does not use probabilistic guessing. Optional selection makes dispatch direct without making the sequence number part of identity.

For a data-only JSON/YAML bundle, an optional `entity_sequence` setting can capture the same configuration at file or group scope. Record-specific overrides are optional too. The setting is importer context and is stripped before model attributes are assigned. When exporting a seed that depends on selection, retain that configuration with the bundle; the selected code remains unchanged. Exact, self-contained code references need no redundant sequence annotation.

Sequence selection does not eliminate vocabulary resolution, collision checks, identity evidence, or database queries. Indexed code/alias bindings can avoid traversing the entire hierarchy on every lookup. Unknown sequences, wrong catalog/type combinations, invalid component counts, and unresolved targets produce explicit errors. Dispatch uses an allowlist of supported resolvers rather than executing a table or class name supplied by input.

An issued sequence's meaning is permanent. Changing a debut year into a season year, changing ordinal scope, or adding/reordering components gets a new number. Alternate league spellings can use the same sequence when its declared vocabulary allows them. Parser fixes that preserve meaning need no new sequence. File-format and importer software versions remain separate from these semantic sequence identifiers; neither can quietly reinterpret an old number. A shared registry keeps older entries available and publishes new ones before dependent bundles use them.

The examples use real names. Codes remain proposed identifiers rather than assertions that these rows are already present. “Existing” means a relevant domain model exists.

| League | `MIC-ALA-BKT-LEAGUE-NBA` | Existing League; full name can be an alias. |
| Four-letter league | `MIC-ALA-SOC-LEAGUE-NWSL` | Existing League type; width is unrestricted. |
| Team | `MIC-ALA-BKT-NBA-TEAM-NYK` | Existing Team. |

| Another athlete | `MIC-ALA-BKT-NBA-CHI-1985-OAKLEY_CHARLES` | Charles Oakley, with Chicago debut context. |
| Season-context athlete alias | `MIC-ALA-BKT-NBA-NYK-SEASON_1994-OAKLEY_CHARLES` | Same person, when the season context is resolved. |

| Organization affiliation | `MIC-ALA-ORGANIZATION-MADISON_SQUARE_GARDEN_SPORTS-TEAM-NYK` | OrganizationAffiliation; add a dated tenure component for repeated affiliations. |
| Coaching tenure | `MIC-ALA-BKT-NBA-NYK-COACH-BROWN_MIKE-FROM_2025_07_07` | Proposed role/tenure referencing Mike Brown's person identity. |
| Player's numbered-game appearance | `MIC-ALA-BKT-NBA-NYK-9394-G1-APPEARANCE-EWING_PATRICK` | Proposed appearance reference; the profile defines season and game-number scope. |

Oakley's NBA record includes Chicago in 1985–86. [NBA player history](https://www.nba.com/player/891/charles-oakley). MSG Sports identifies the Knicks among its teams. [Company portfolio](https://www.msgsports.com/our-company/). Mike Brown was hired by the Knicks on July 7, 2025. [NBA announcement](https://www.nba.com/news/knicks-mike-brown-new-coach).

A team, its membership, its season participation, and its organization's affiliation have distinct identities. A coach's person identity survives different coaching tenures.

Unknown debut information can remain a sourced lead until resolved or use a documented source-anchored code. Do not invent dates or use a universal `UNKNOWN` placeholder as an identity.

Changing teams, names, sports, or player/coach roles normally adds relationships or aliases rather than another person. The game-appearance example illustrates the syntax; participating athletes are established from a games-played source before seeding.

## 6. Compact game, inning, at-bat, and pitch references

Games played and appearances may be near-term work. Pitch and inning detail are future code examples; no statistical implementation is planned at this stage. A compact or fully numeric profile can be the default, with longer descriptive forms supported as alternatives.

Mike's examples:

```text
MIC-ALA-BSB-MLB-PIT-2526-G20-P8
MIC-ALA-BSB-MLB-PIT-2526-G25-IT4-P8
```

| Entity | Local code | Meaning within its profile |
| --- | --- | --- |
| Pirates' twentieth game | `BSB-MLB-PIT-2526-G20` | Game 20 within the team's declared season/edition. |
| Eighth pitch of that game | `BSB-MLB-PIT-2526-G20-P8` | Pitch ordinal scoped to the game. |
| Top of the fourth in game 25 | `BSB-MLB-PIT-2526-G25-IT4` | `IT4` is inning 4, top half. |
| Eighth pitch of that inning half | `BSB-MLB-PIT-2526-G25-IT4-P8` | Pitch ordinal scoped to the inning half. |
| Bottom of the fourth | `BSB-MLB-PIT-2526-G25-IB4` | Bottom half of inning 4. |
| Third at-bat in game 20 | `BSB-MLB-PIT-2526-G20-AB3` | At-bat ordinal scoped to the game. |
| Eighth pitch of that at-bat | `BSB-MLB-PIT-2526-G20-AB3-P8` | Pitch ordinal scoped to the at-bat. |
| Third at-bat in top of the fourth | `BSB-MLB-PIT-2526-G25-IT4-AB3` | At-bat ordinal scoped to that inning half. |

`AB` is the code label for at-bats. The immediately enclosing component determines what an ordinal counts. The supplied `2526` is retained as a season/edition token; its expansion belongs in the profile rather than being inferred from its digits.

A game is one entity even though each participating team has its own game number. The Pirates' game-20 code and the opponent's corresponding team/game code can be registered references to that same game. These aliases do not create duplicate games.

The profile will eventually specify game numbering, doubleheaders, postponements, resumptions, and event counting. Issued references remain bound to their original occurrences when source numbering is corrected. No pitch results, counts, or timestamps are asserted by these syntax examples.

## 15. What seed replay should do

The default policy is **preserve**. This proposal interprets “without overwriting existing data” literally.

| Situation | Default action |
| --- | --- |
| Code and target are missing | Create the defined entity and bind its codes. |
| Same identity and same values already exist | Leave the record unchanged. |
| Same identity, new alias | Add the alias if its binding is conflict-free. |
| Missing relationship | Add the explicit relationship after both endpoints resolve. |
| Missing field or unknown value | Report proposed enrichment; filling it requires an explicit per-field enrichment policy. |
| Existing value differs | Preserve it and record a conflict with both values and provenance. |
| Existing relationship omitted from a file | Preserve it. Absence is not an instruction to remove it. |
| Field absent from incoming data | Preserve it. |
| Explicit incoming null | Preserve the existing value under ordinary replay; clearing needs an explicit amendment. |
| Previously bound target was deleted | Reconstruct it from an available definition and repair the local binding; never attach to whichever row reused its old numeric ID. |
| Identity was deliberately retired, merged, or tombstoned | Follow the recorded retirement or merge policy; ordinary replay does not undo it. |
| Code points to another type or incompatible identity | Block that unit of import and report the collision. |
| Required reference is missing or ambiguous | Block the dependent unit; do not silently skip it or select an arbitrary row. |

Approved corrections use an explicit amendment with a target code, intended change, source, and expected prior value or revision. This supports new knowledge without letting an older file silently reverse a later correction. Identity equivalence and merges are explicit amendments too.

Amendments have durable library identities; a possible correction-code shape is `MIC-ALA-AMENDMENT-OAKLEY_CHARLES-BIO-SOURCE_CORRECTION_1`. They declare prerequisite amendment codes and expected prior semantic values or a portable content revision; database row IDs, timestamps, and local revision counters are excluded from those preconditions.

If a definition starts at A and accepted amendments establish A→B→C, reconstruction derives C by applying that declared chain in order. The importer plans amendment dependencies as well as entity dependencies, and validates the final accepted projection before creating a missing target. An unrelated same-field branch is a conflict to resolve, not a file-order tie-break.

On ordinary replay, already applied or superseded amendments do not run backwards. The ledger records their durable identities and verifies the effective current state. Original observations superseded by an accepted amendment remain provenance, rather than recurring overwrite attempts. If a local edit differs from the accepted projection, preserve it and report the difference. A rebuild of a missing record uses the current accepted projection, not an arbitrary older base file.

Large catalogs should not need every file to be manually ordered. Proposed importer phases:

1. Index definitions, aliases, sequence configurations, registry revisions, source keys, and code-based references across selected manifests.
2. Validate conflicting definitions, derive accepted projections from ordered amendments, and resolve exact identity/alias bindings.
3. Plan entity and amendment dependency graphs. Create required parents before children; defer optional links. A cycle of required associations is an explicit model/import problem, not something codes magically remove.
4. Apply records and relationships in bounded, atomic units. Report independent successes and blocked units with their reasons.
5. Store source revision, content checksum, result, conflicts, and resolved references in a run ledger.

Database uniqueness and transaction locking handle concurrent imports. Do not perform a name lookup for every occurrence or keep the entire massive catalog in one process-wide hash. Use indexed code resolution, batch prefetching, bounded caches, and dependency-aware chunks.

Checksums can skip already observed content only after verifying required targets and dependencies still exist. A file that ran successfully yesterday may need replay today because a catalog row was removed.

## 17. Rebuildable catalog versus unique user history

The seed library can become the durable source of accepted catalog knowledge. To make that true, every accepted change must reach a replayable manifest or amendment, including aliases, merges, relationship corrections, and retirements. Editing only the live database leaves knowledge outside the library.

Routine replay and full reconstruction have different responsibilities. A new importer must distinguish an accidentally missing target from a deliberate deletion. Tombstones and merge mappings belong in the durable library.

For the first pilot, the entire database can be rebuilt and there are no surviving dependents to reattach. For any later partial rebuild that preserves dependents, catalog relationships use local codes with bundle scope or qualified foreign references in manifests. Personal records such as ratings or AimSteps would need a retained target code or a durable identity binding and a controlled reconciliation step. Existing numeric-only foreign keys do not become safe merely because entity codes are added elsewhere.

Public catalog replay cannot reproduce an account, personal rating, private Aim, payment, or unexported game attempt. Those still require durable application storage and appropriate backups. The opportunity is to make sports, political, music, and practice knowledge reproducible from the library rather than repeatedly reconstructing it through database backups or fresh ingestion.

## 18. From sources to thousands of files

Proposed pipeline:

```text
source capture
  → structured extraction
  → code construction and identity reconciliation
  → source-backed entity / relationship / claim manifests
  → validation and conflict handling
  → committed library
  → deterministic replay
```

Acquisition and replay are separate stages. Replaying accepted files needs no fresh scrape, network request, or model call. Raw captures, source keys, parser/extractor version, and provenance let us revise the extractor later without pretending a newly interpreted claim is already accepted.

Where a source supplies reliable IDs, retain them as scoped external aliases. A provider's athlete ID, event ID, accession number, or catalog number can be a numeric or alphanumeric token without being a local database primary key.

Partition files by source family, sport/league, season, event, subject, or a bounded batch. File paths are organizational and may change; issued identity codes do not depend on filenames.

Automate uncontested matches, new definitions, and schema validation. Source conflicts, uncertain people, changed sequence numbers, unsupported entity types, and contradictory evidence are the exception queue. The default policy can be narrow without requiring a manual import ceremony for every ordinary file.

The library needs manifests that declare dependency sets and external catalog versions. Cross-app replay can use exported identity registries locally rather than contacting another running app for each reference.

Spindrift's reviewed importer is a useful starting pattern for conflict reporting and provenance. Its ledger is not yet a universal semantic-code registry or a complete deleted-record reconstruction mechanism.

Proposed stages:

1. **Specify the shared contract:** prefix and optional numeric sequence registries, grammar profiles, normalization, alias scope, retirement/merge rules, and default preservation behavior.
2. **Pilot AthleteAce identities from an empty database:** Sport, League, Team, Player, Season, and Campaign; define their required parents and associations in the library and create local-code/alias bindings during import. No legacy-row migration is needed.
3. **Implement and prove replay:** repeated runs, overlapping files, concurrent imports, conflicting values, changed IDs, and deliberately deleted targets.
4. **Consider games played next:** Game identities and athlete appearances can precede statistics. Uniforms, race laps, pitches, and other detailed types remain future extensions with their own recipes.
5. **Integrate the other catalogs:** preserve each app's actual domain boundaries and extend its importer rather than mechanically replacing slugs.
6. **Add cross-app practice claims and the fan resolver:** reuse issued identities and surface evidence and ambiguity.

Open design questions can be settled incrementally: final catalog tokens; shared registry distribution; exact collision recipes; enrichment policies for unknown fields; first supported event source; the intended Jev component; and where the public resolver is hosted.

### Before the first seed trial

The design is sufficient to begin a small pilot without specifying every future sports or cross-app recipe. Before generating the large library, establish these behaviors in the pilot:

1. **Separate configuration and identity from model fields.** Today's player seeder forwards arbitrary JSON keys into `assign_attributes`; adding `code` or an `entity_sequence` setting to its current player objects is not sufficient. A new code-aware envelope/adapter extracts metadata, supports optional scoped `sequence_is` configuration, validates accepted attributes and associations, and resolves supported constructions deterministically. A clean rebuild lets this pilot use the new path directly, without preserving the legacy loading behavior.
2. **Define complete identities and dependencies.** Start with a small selected set of Sports, Leagues, Teams, and Players and persist unique catalog code/alias bindings as they are created. Supply required parents and associations from the library, adjusting the schema if needed. Missing debut-team information is not inferred from a roster filename. A changed current team must still resolve the same person; contextual aliases require evidence rather than creating another Player.
3. **Make replay preservation real.** The current helper assigns incoming fields. The pilot creates missing records and links, preserves existing values and omitted relationships, and reports conflicts. An optional enrichment policy and explicit amendments can follow. A failed required dependency must be visible; the pilot cannot count a skipped record as a successful import.
4. **Prove complete reconstruction and reference safety.** Build an empty database from the selected library, run it again, then rebuild from empty with a different file order and different numeric IDs. Compare semantic records and code-based relationships. Also test overlapping bundles and restoration of a missing target. No existing user history needs to survive this pilot; later partial-rebuild support is a separate concern. Deliberate retirement remains distinct from accidental absence.
5. **Attach sources and temporal scope.** Existing files include roster snapshots and mutable attributes such as active status. Treat those as dated observations or relationships rather than identity facts. Define the entity/model boundary and evidence required for each supported recipe. Library growth should not amplify stale roster assertions into timeless truths.
6. **Validate batches before writing.** Provide a dry-run report for duplicate/conflicting codes, unsupported selected sequences, ambiguous constructions, unknown fields, missing parents, planned creations, and preserved differences. Start with a few small bundles and bounded transactions. Record source and sequence-registry revisions; a successful prior run does not authorize skipping targets that are now missing.

The first trial can reuse source material about a few teams and a small set of real athletes with sourced debut anchors, while creating every required row in a clean database. Games and appearances are the next optional layer. No pitch, timing, or other statistics implementation is required to demonstrate repeatable, code-based seed replay. Expand generation once this same small library can be rebuilt reliably and replayed without duplicates or unintended changes.
